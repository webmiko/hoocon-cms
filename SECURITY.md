# Security Policy

Политика ответственного раскрытия уязвимостей для [Hoocon CMS](https://hoocon.ru).

Технический baseline проекта: [docs/security-baseline.md](docs/security-baseline.md).

## Supported versions

Исправления безопасности выпускаются для активной ветки разработки и
последнего production-релиза на `main` / `develop`. Старые теги — по
согласованию, если ещё на поддержке.

| Версия / ветка | Поддержка security-fix |
|----------------|------------------------|
| `main` (prod)  | Да |
| `develop`      | Да |
| Старые теги    | Только по запросу |

## Reporting a vulnerability

**Не** создавайте публичный GitHub Issue с описанием уязвимости до
согласования с нами.

### Предпочтительно

1. **GitHub:** вкладка **Security → Report a vulnerability** (private
   security advisory) в этом репозитории — если репозиторий public и
   функция доступна.
2. **Email:** [sales@hoocon.ru](mailto:sales@hoocon.ru) с темой
   `Security: Hoocon CMS`.

### Что указать в отчёте

- краткое описание и тип проблемы (XSS, IDOR, RCE, утечка данных и т.д.);
- шаги воспроизведения (URL, роль пользователя, запрос/ответ);
- влияние (какие данные или системы под угрозой);
- PoC / скриншоты — по возможности;
- ваша оценка критичности (необязательно).

Не включайте в отчёт реальные пароли, токены, персональные данные клиентов
или содержимое production `.env`.

## What we expect from reporters

- разумный срок на исправление до публичного раскрытия (координируемся);
- не тестировать на production сверх необходимого (без DoS, без массовой
  выгрузки данных);
- не нарушать закон и конфиденциальность третьих лиц.

## Response timeline (ориентир)

| Этап | Срок |
|------|------|
| Подтверждение получения | 3 рабочих дня |
| Первичная оценка / severity | 7 рабочих дней |
| Исправление критичных (RCE, утечка PII, обход auth) | по ситуации, приоритет |
| Публичное раскрытие | после выката fix или по договорённости |

## In scope (примеры)

- публичный сайт `hoocon.ru` и API (`/api/…`), Admin `/admin/`;
- RFQ, поиск, каталог, загрузки media, SEO/SPA head injection;
- аутентификация staff (OTP, break-glass), утечки через serializers;
- инфраструктура деплоя **только** если уязвимость воспроизводится из
  опубликованного кода репозитория.

## Out of scope

- социальная инженерия, фишинг сотрудников;
- физический доступ к офису / VPS без связи с кодом;
- уязвимости сторонних сервисов (Яндекс 360, reg.ru, GitHub), не
  контролируемых репозиторием;
- сканирование без доказательства эксплуатации (теоретический «missing
  header» без impact).

## Safe harbor

Мы не будем преследовать исследователей, которые добросовестно следуют
этой политике и не причиняют вред пользователям или данным.
