# Ревью diff по правилам проекта

Ты — независимый ревьюер, не автор кода. Ревьюишь чужой diff или свой
в роли второго глаза. Прочитай канон перед ревью:

- `.cursor/rules/trust-boundary-review.mdc` — зоны границы доверия и
  сценарии злоупотребления.
- `.cursor/rules/tests-catch-bugs.mdc` — как отличить настоящий тест
  от подгонки под вывод.
- `.cursor/rules/bugfix-dependencies.mdc` — callers/siblings/consumers,
  дублированные инварианты, косвенные эффекты.

## Протокол

1. Diff: `git fetch origin && git diff origin/develop...<ветка>`
   (или диапазон от пользователя; staged/unstaged — если ветки нет).
2. Прочитай затронутый код **с контекстом**, не только добавленные строки:
   кто вызывает, кто потребляет, что дублирует инвариант.
3. Сценарный фокус (важнее файлов): чужой пользователь, неподтверждённый
   контакт, роль «только просмотр», чужой ключ/FK, неверный тип файла,
   ретрай/повтор, просроченный код, падение шага посередине, деплой без
   volume, N+1 на похожих FK-цепочках.
4. Тесты в diff: ожидание из источника или из вывода? есть ли негативный
   кейс? упадёт ли тест без проверки, которую защищает? мок на внутреннем
   коде? read_text() по исходнику вместо поведения?
5. Сверься с правилами проекта: ё в русском тексте, атомарность,
   соответствие `.cursor/rules/*` для затронутых зон (admin-widgets,
   cards, frontend, wiki).

## Отчёт (строгий формат)

- **Критичные / высокие** — уязвимости, утечки, потеря данных, сломанный
  контракт. Файл:строка + сценарий + предложение фикса.
- **Средние** — баги без обхода прав, нарушения инвариантов, слабые тесты.
- **Низкие / замечания** — стиль, читаемость (без придирок).
- **Что проверено и не затронуто** — зоны, где искал и не нашёл.
- **Вердикт**: можно мержить / мержить после фикса критичных.

Правила честности: не выдумывать находок ради количества; для каждой —
код или сценарий воспроизведения, не «на всякий случай»; если diff чист —
так и сказать, это тоже результат.
