# План: сравнение SKU по ТТХ

Дата: 2026-07-20  
Статус: **MVP реализован** (итерация 6).  
Цель: инженер/закупщик быстро сопоставляет 2–N моделей Hoocon по характеристикам
и уносит результат в RFQ / коллеге.

### Согласовано (2026-07-20)

| Вопрос | Решение |
|--------|---------|
| Лимит SKU | **4** (desktop и mobile) |
| Family lock по категории | **Нет** — свободное сравнение; неприменимые ТТХ → «—» |
| API | **Не только клиент** — batch `GET /api/catalog/compare/` + FE tray/URL |
| «Только отличия» по умолчанию | **Да** (вкл) |
| Старт кода | **MVP shipped** — `/compare`, tray, checkbox на карточке, кнопка на PDP |

---

## 1. Зачем (боль)

- В каталоге ~180 SKU, 7 категорий (воздушные приводы, пружинные, ОЗК/дымоудаление,
  шаровые краны). Карточки показывают 5–6 highlights — для выбора между близкими
  сериями (DA4MU vs DA6MU, 24 В vs 230 В) этого мало.
- Belimo/OEM дают SelectPro / табличные каталоги PDF. Hoocon закрывает боль
  **локальным side-by-side** без корзины (v1: только RFQ).
- Сравнение ≠ подбор/замена Belimo (`/analog-belimo` — отдельная фича итерации 6).

---

## 2. Рекомендуемый UX (канон B2B)

### 2.1. Три поверхности

| Поверхность | Роль |
|-------------|------|
| **Точка входа** | Чекбокс / «В сравнение» на **карточке каталога** и **PDP** |
| **Tray (полоса)** | Фикс. снизу: миниатюры выбранных SKU, счётчик, «Сравнить», «Очистить» |
| **Страница `/compare`** | Таблица: строки = характеристики, столбцы = SKU |

Не делать отдельный «избранное» / wishlist — в плане v1 явно без Cart/Wishlist.
Tray живёт только пока есть ≥1 SKU; на `/compare` tray можно скрыть или
оставить как «редактировать набор».

### 2.2. Лимиты

| Параметр | Рекомендация | Почему |
|----------|--------------|--------|
| Минимум для кнопки «Сравнить» | **2** | Одна модель бессмысленна |
| Максимум | **4** (desktop и mobile) | Согласовано; больше — таблица нечитаема |
| Хранение набора | `localStorage` + **URL** | Shareable для B2B |

### 2.3. Таблица сравнения

```
                 | [фото] DA4MU24   | [фото] DA6MU24   | [+] добавить
Артикул          | DA4MU24          | DA6MU24          |
Аналог Belimo    | …                | …                |
─────────────────┼──────────────────┼──────────────────
Крутящий момент  | 4 Нм             | 6 Нм      ← diff
Напряжение       | 24 В=            | 24 В=
Управление       | Пропорциональное | Пропорциональное
…
```

Поведение:

1. **Sticky** первая колонка (название параметра) + sticky шапка SKU при скролле.
2. **Горизонтальный скролл** на mobile (столбцы ≥ ~160 px).
3. **Подсветка различий** (строка, где значения не совпадают) — toggle
   «Только отличия» (**default on**, согласовано).
4. Группировка строк как на PDP: Электрические / Функциональные / … через
   `attribute_groups` / те же ключи, что `attr_groups.py`.
5. Пустая ячейка → «—» (параметр не применим, напр. Kvs у воздушного привода;
   при свободном сравнении семейств таких ячеек будет больше).
6. CTA внизу столбца: «Запросить цену» → `#rfq` / `/consultation` с
   prefill артикулов (если LeadForm уже умеет `sku=` — расширить списком).
7. Удалить столбец (×), добавить SKU (поиск/модалка из той же категории).

### 2.4. Карточка каталога (интеграция)

Сейчас карточка — `article` + stretched `cardHit`. Кнопка «Сравнить» — как
ссылка «спецзаказ»: `position: relative; z-index: 2` (класс `cardInteractive`),
`stopPropagation` не нужен (hit — сосед, не родитель).

Визуал: компактный чекбокс слева сверху медиа **или** текстовая кнопка в футере
карточки («Сравнить»). Предпочтение: **чекбокс на медиа** (не конкурирует с
«Паспорт и ТТХ»).

### 2.5. Ограничение по категории

**Согласовано: без family lock.** Можно смешивать приводы и краны; строки без
значения у части SKU показывают «—». Опционально позже: мягкая подсказка
(не блокер), если в наборе >1 категории.

### 2.6. SEO / URL

- Маршрут: `/compare?skus=slug-a,slug-b,slug-c` (порядок = порядок столбцов).
- Canonical: `/compare` без query **или** с отсортированными slug — лучше
  **noindex** для query-вариантов (как у фильтров каталога), чтобы не плодить
  тонкий контент в индексе.
- Пустой `/compare` — empty state: «Выберите 2–4 модели в каталоге» + ссылка
  в `/catalog`.

## 3. Реализация (техника)

### 3.1. Frontend (основной объём)

| Модуль | Назначение |
|--------|------------|
| `hooks/useCompareTray.ts` | Add/remove/clear, лимит 4, sync URL↔storage |
| `components/CompareTray.tsx` | Нижняя полоса |
| `pages/ComparePage.tsx` | Таблица + toggles |
| `utils/compareMatrix.ts` | Свести N SKU → строки `{key, label, values[], isDiff}` |
| `api/client.ts` | Уже есть detail; для batch — см. API ниже |

Состояние:

```ts
// localStorage key e.g. hoocon.compare.v1
{ slugs: string[]; updatedAt: string }
```

При открытии `/compare?skus=…` — URL **побеждает** storage (шаринг ссылки).

### 3.2. Backend API

**Вариант A (рекомендуется для MVP):**  
`GET /api/catalog/skus/?slug__in=a,b,c` или `?slugs=a,b,c` с расширенным
сериализатором list → для compare нужны **highlights + attribute_groups**, не
только list-card. Проще:

**Вариант B:**  
`GET /api/catalog/compare/?skus=slug1,slug2,slug3`

Ответ:

```json
{
  "skus": [ /* SKUDetail-lite: slug, name, sku_code, image, analog, highlights, attributes */ ],
  "rows": [
    {
      "key": "moment",
      "name": "Крутящий момент",
      "group": "functional",
      "values": ["4 Нм", "6 Нм"],
      "diff": true
    }
  ],
  "warnings": []
}
```

Плюсы B: один round-trip, единая нормализация строк, diff на сервере
(детерминизм). Минусы: новый endpoint.

**Вариант C:** N параллельных `GET /api/catalog/skus/{slug}/` на клиенте.  
Плюсы: ноль backend. Минусы: N запросов, дублирование matrix-логики на FE,
сложнее тесты канона.

Рекомендация: **B** с переиспользованием `highlights_for_sku` +
`group_attribute_rows` / `_sku_attribute_rows`. Лимит query: max 4 slug,
validation 400 если больше / неизвестный slug.

Throttle: как у публичного read (существующий catalog throttle).

### 3.3. Матрица характеристик (канон ключей)

Порядок строк — приоритет фасетов + EXTRA highlights, затем остальные attrs
по `ATTR_GROUP_ORDER`:

1. Базовый блок (всегда, если есть): момент, напряжение, управление, площадь /
   DN+Kvs (по family), aux, runtime, control_signal, feedback_signal, IP,
   analog Belimo.
2. Полный блок (toggle «Все ТТХ»): остальные из attribute_groups.

Нормализация значений — **та же**, что в карточках (`normalize_*` в
`tech_copy` / facets), иначе diff ложноположительный
(`24 В` vs `24 В=`).

Diff: строковое сравнение после `casefold` + схлопывание пробелов; для чисел
опционально позже (не в MVP).

### 3.4. Безопасность / scope

- Публичный read-only; цены — как в list/detail (`show_prices`).
- Нет PII; нет записи на сервер (набор только client-side).
- Не путать с wishlist: иконка в шапке — только **бейдж счётчика** при n>0,
  опционально (можно ограничиться tray).

## 5. Критерии приёмки (MVP)

1. С каталога можно добавить 2–4 любых SKU; tray показывает набор.
2. `/compare?skus=a,b` открывается у другого пользователя с тем же набором.
3. «Только отличия» включено по умолчанию; строки-diff подсвечены.
4. Неприменимый параметр — «—», не пустая дыра (в т.ч. при смеси категорий).
5. Удаление SKU и «Очистить» работают; >4 — отказ с понятным текстом.
6. Нет вложенных `<a>` на карточке; a11y: чекбокс с `aria-label`.
7. `noindex` или canonical без бесконечных комбинаций slug.
8. Pytest + FE smoke зелёные; pre-commit checkup перед коммитом.

## 6. Риски

| Риск | Митигация |
|------|-----------|
| Грязные EAV-slug (`attr-…`) ломают ключи строк | Матрица по **facet key** / нормализованному name, не сырому slug |
| Смешение семейств | Много «—»; без блокера (согласовано); позже мягкая подсказка |
| Карточка + stretched link | Паттерн как у SignalSpecValue (`cardInteractive`) |
| Scope creep (избранное, аккаунты) | Только tray + URL; без бэкенд-аккаунта |
| Ложные diff из-за единиц | Те же `normalize_*`, что каталог |
